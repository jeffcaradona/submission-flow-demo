# Submission flow demo

A single-repo walkthrough of the "submit data" story: accept quickly (`202`), process after the response, and push status over SSE. The three application domains are real directories, and the database is a mock of `node-mssql`.

Node ESM, Express 5, Eta templates. Server-rendered pages only, no SPA.

```
src/
  frontend/     Express + Eta. Form POST -> 303 redirect, SSE proxy, pages
    views/        *.eta templates (layout + one per page)
    public/       live-status.js, the only client script (progressive enhancement)
  api/          Express JSON API. Talks to the database only through repo.js (stored procedures)
  mssql-mock/   In-memory stand-in for node-mssql and the stored procedures
  main.js       Starts API (:3001) and front end (:3000) together
test/           node:test, end to end across all three domains
```

## Run

```
npm install
npm start            # front end http://127.0.0.1:3000, API :3001
npm test
```

Knobs: `MOCK_PROCESS_MS` (default 3000, how long `usp_ProcessUserRequest` takes), `PORT`, `API_PORT`, `HOST`, `DEMO_USER_ID`.
Submit a package named `POISON` to see the `Failed` path.

## The flow

1. `GET /submit` renders the form with a fresh idempotency key (hidden field), minted when the form is opened.
2. `POST /submit` -> front end -> `POST /submissions` with `Idempotency-Key`.
3. API calls `usp_InsertUserRequest` (writes the whole body as one line of JSON; returns `request_id` + `is_new`) and answers `202` immediately.
4. Only if `is_new = 1`, the API then calls `usp_ProcessUserRequest`. It claims the row (`Accepted` -> `Processing`), does the work, and finishes as `Completed` or `Failed`.
5. Every page loads `live-status.js`, which opens `/events`. On connect the API sends a `snapshot` event per recent request (`usp_GetUserRequests`); when processing finishes it sends a `status` event to any open connection.
   The connection is registered before the snapshot is read and live events are buffered until the snapshot is written, so a completion can't fall in the gap.
6. The script updates any matching rows on the page and toasts once for requests it was watching, even if they finished while the user was between pages.

## The mock

`mssql-mock` implements the slice of node-mssql the app uses: `ConnectionPool`, `request().input(name[, type], value).execute('dbo.proc')`, `recordset`/`recordsets`/`output`/`returnValue`, `RequestError` (`code: 'EREQUEST'`, `number`), and `ConnectionError`. The unique index on `(user_id, idempotency_key)` throws error 2627 like SQL Server, and the insert proc handles it with try-insert / catch-duplicate.

Swapping to the real driver: `npm i mssql`, change `"#mssql"` in `package.json` `imports` to `"mssql"`, and drop the `mock` key from the pool config in `src/api/server.js`. The stored procedures themselves would be T-SQL equivalents of `src/mssql-mock/procs.js`.

Not modeled: transactions and isolation levels, parameter type validation, multiple result sets from a single call, and anything about timeouts or pool sizing.
